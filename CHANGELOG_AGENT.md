### Анализ текущей архитектуры по трем ключевым направлениям

#### 1. Блокчейн и кошельки (Wallets & Ledger)
- **Текущее состояние:** 100% Mock / эмуляция внутри локальной SQLite базы данных.
  - Генерация адресов: функция `_ensure_wallet` в `apps/api_py/store.py` формирует псевдо-адреса вида `0xcmir{uuid.uuid4().hex}`.
  - Ledger транзакций: таблица `blockchain_records` генерирует SHA-256 хеш с солью и сетью `"cmir-ledger-stub"`.
  - Токены: `balance_st` (Security Tokens) и `balance_ut` (Utility Tokens) хранятся как числовые поля в таблице `wallets`.
  - Начисление (Airtime): логика начисления UT за нахождение в кадре (`POST /pois/{id}/airtime`) и просмотры (`POST /views`).
- **Узкие места и риски:**
  - Отсутствует интеграция с реальным блокчейн-провайдером (RPC Web3, смарт-контракты ERC-20/SPL/Jetton, кошельки Web3).
  - Риск накрутки/инфляции баланса UT через клиентские вызовы без серверной валидации присутствия.
  - При переходе на реальный блокчейн категорически запрещено хранить сид-фразы и приватные ключи на бэкенде.

#### 2. Обработка видеопотоков (Video Ingest, Processing & Delivery)
- **Текущее состояние:**
  - **Медиасервер:** MediaMTX (версия `bluenviron/mediamtx:latest`) в `apps/ingest/docker-compose.yml`. Поддерживает RTMP (:1935), RTSP (:8554), HLS (:8888), API (:9997).
  - **Компьютерное зрение (Face Worker):** модуль `cmir_face` (`apps/face-worker/`) на Python + SCRFD (InsightFace/ONNX Runtime) + MediaPipe + ByteTrack для трекинга и маскирования области глаз (`eye_mask.py`).
  - **Трансляция и релей:** `apps/api_py/local_relay.py` порождает процессы FFmpeg для захвата и передачи потоков.
- **Узкие места и риски:**
  - **Критический архитектурный боттлнек:** `apps/api_py/server.py` построен на стандартном однопоточном синхронном `http.server.HTTPServer`. Любой блокирующий вызов (например, `probe_stream_url` при проверке камер) останавливает обработку всех входящих запросов API.
  - **Каскадное перекодирование:** многократная цепочка RTMP/RTSP Ingest → Frame Decode → CV Inference → FFmpeg RTMP Encode → MediaMTX → HLS Packaging вызывает задержку (3-8 сек) и высокую утилизацию CPU.
  - **Неуправляемые процессы FFmpeg:** спавн FFmpeg через `subprocess.Popen` без супервизора может приводить к процессам-зомби при аварийном завершении воркера.
  - **Отсутствие кэширующего прокси перед HLS:** прямая раздача сегментов HLS с MediaMTX на сотни клиентов перегрузит сетевой стек и I/O VPS.

#### 3. Безопасность, соответствие (Compliance) и секреты
- **Текущее состояние:**
  - Локально реализовано шифрование биометрических векторов (AES-CBC с HMAC) через `CMIR_DATA_KEY`.
  - В prod-режиме (`CMIR_ENV=prod`) сервер требует обязательного задания `CMIR_DATA_KEY`, `CMIR_ADMIN_PASSWORD` и `CMIR_WORKER_TOKEN`.
  - В `.gitignore` корректно внесены `.env`, `*.db`, `data/buffers/`, `data/masks/`.
- **Выявленные пробелы и риски:**
  - В проекте отсутствует шаблон `.env.example`, описывающий все требуемые переменные окружения.
  - В тестовых скриптах (`scripts/start-lab.sh`, `scripts/run-tests.sh`) зашиты дефолтные тестовые ключи (для lab-режима это допустимо, но важно гарантировать их неприменение в prod).
  - Отсутствуют готовые Dockerfile для API, Face Worker и Web-интерфейса, а также общий `docker-compose.prod.yml`.
  - Отсутствует конфигурация Reverse Proxy (Caddy / Nginx) с автоматическим выпуском SSL-сертификатов Let's Encrypt.
  - Отсутствует CI/CD пайплайн (GitHub Actions) для автоматического тестирования и валидации безопасности при пушах.
